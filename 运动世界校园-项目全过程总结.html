3第二阶段:发现代码被完整加密

这是整个项目的转折点 —— 静态修改这条路在这里被彻底堵死。

3.1 反常的 dex 文件

apktool 解包 317 MB 的 APK 只用了 3 秒,这个速度对一个 73.8 MB 的 dex 来说极不正常。 解析 classes.dex 的 112 字节文件头后,真相浮出水面:

dex 头字段数值含义
file_size77,391,616文件确实是 73.8 MB
class_defs_size30整个文件只有 30 个类
method_ids_size660只有 660 个方法
data_size50,336真实数据只有 50 KB
结构性的矛盾:73.8 MB 的文件里只有 50 KB 有效数据。 这意味着约 73.7 MB 是加密载荷。

3.2 网易易盾加固

apktool 解出的全部 30 个 smali 文件都位于 com/netease/nis/wrapper/, 这是网易易盾加固的典型特征:

com/netease/nis/wrapper/
├── MyApplication.smali            51.3 KB  应用入口被替换
├── MyJni.smali                    32.4 KB  调用 libnesec.so
├── NEDialog.smali                 17.2 KB  篡改检测弹窗
└── plugin/
    ├── InstrumentationProxy.smali  3.8 KB  劫持 Activity 生命周期
    └── a~g.smali                   运行时解密并加载真 dex

配合原生库证据:libnesec.so、libnetseckit-4.2.4.so (易盾)、libijiami_1011.so(爱加密)。

3.3 为什么这条路走不通

✕
无 Root 无法脱壳
真代码在运行时才被解密加载,静态拿不到。
✕
重打包必然破坏签名
任何 smali 修改都要重新签名,而签名一变,易盾的完整性校验就会触发。
✕
反调试与反注入
InstrumentationProxy 劫持生命周期,NEDialog 在检测到篡改时弹窗拦截。

结论:「脱壳 → 修改 smali → 重打包 → 重签名」这条常规路线, 在这个样本上投入产出比极差且大概率失败。必须换思路。

4第三阶段:转向网络层屏蔽

既然改不了 App,那就改它看到的世界 —— 在网络层把广告请求掐断。

4.1 方案的可行性依据

关键在于:加固保护的是 代码,但没有、也无法保护 网络请求。 广告 SDK 要投放广告,就必须向自己的服务器发请求 —— 而那些请求会经过系统网络栈, 可以被本地 VPN 拦截。

Android 从 4.0 起提供 VpnService 机制, 普通应用即可创建本地 VPN 接管全部流量,完全不需要 Root。 用户手机上已有的 Clash 客户端本身就是基于这个机制运行的。

4.2 一个意外的关键发现

在解包产物 res/xml/network_security_config.xml 中,发现了开发者自己留下的配置 (含中文注释):

<base-config cleartextTrafficPermitted="true">
    <trust-anchors><certificates src="system" /></trust-anchors>   ← 业务域: 只信系统证书
</base-config>

<domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="true">i.snssdk.com</domain>          ← 穿山甲
    <domain includeSubdomains="true">pangolin.snssdk.com</domain>
    <domain includeSubdomains="true">mi.gdt.qq.com</domain>          ← 腾讯优量汇
    <domain includeSubdomains="true">dig.bdurl.net</domain>           ← 百度
    <trust-anchors>
        <certificates src="user" /> //信任用户自己安装的证书
        <certificates src="system" />
    </trust-anchors>
</domain-config>

这段配置无意中公开了 10 个广告域名,而且证明它们与业务域走不同的信任链 —— 为后续的定向分析提供了官方标注过的目标清单。

4.3 方案选型

方案可行性原因
动态 Hook(LSPosed / Frida)排除硬性要求 Root
静态脱壳改包重签名排除无 Root 无法脱壳,重签名必触发易盾
修改 hosts排除需 Root
本地 VPN 做域名拦截采用免 Root、不改 APK、易盾无法察觉
这个方案的核心优势:不修改 APK 的任何字节 → 签名不变 → 网易易盾的签名校验、完整性校验、反调试全部不会触发。 同时可随时一键撤销,不留痕迹。

  • 剔除了一次误判:g.alicdn.com 是淘宝图片 CDN,屏蔽会导致图片加载失败

8技术边界:哪些做不到

如实说明方案的适用边界 —— 这比夸大效果更有价值。

8.1 已排除的所有其他可能

假设结论排除依据

8.2 域名屏蔽原理上够不着的部分

服务端下发广告。如果广告数据是随正常接口响应一起返回的, 那么它与业务数据走同一个 HTTPS 连接、同一个域名。域名规则只能判断 「连不连这个域名」,无法判断「这个连接返回的内容是广告还是正常数据」。

而该 App 的业务域 iydsj.com 绝不能屏蔽 —— 登录、跑步、发现页、上传全部依赖它。

8.3 为什么 HTTPS 解密也解决不了

那 10 个信任用户证书的域名,全部是第三方广告平台。 而业务域走 base-config,只信任系统证书 —— 在无 Root 的情况下无法向系统证书库安装 CA,因此业务域流量在密码学上不可解密。

这是开发者有意设计的隔离:广告域名放行用户证书(便于 SDK 调试), 业务域严格锁定系统证书。

  • 构建出 190 条广告域名拦截规则,覆盖全部可发现的广告平台
  • 与用户订阅合并为可直接导入的配置,翻墙功能零影响
  • 实测验证:459 次广告连接被拦截 / 85% 拦截率
  • 产出隐私化分享包,可安全分发给他人

未完成(技术边界)

  • 服务端下发的广告 —— 与业务数据同域名同连接,域名层原理上无法区分
  • HTTPS 解密业务域 —— 业务域只信任系统证书,无 Root 无法安装 CA
  • 修改 App 本身 —— 易盾加密 + 签名校验,不改包是唯一可行前提

最终方案

以网络层域名拦截为主,配合界面层自动点击工具。 这个组合在不获取 Root、不修改 APK 的前提下,把可行的部分做到了极限 —— 而这恰好也意味着零封号风险、可随时撤销、应用升级后规则依然有效。
